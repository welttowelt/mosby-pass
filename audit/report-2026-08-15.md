# Veilpass contract security checkpoint

Date: 2026-08-15
Scope: `src/lib.cairo`, `tests/test_veilpass.cairo`, `Scarb.toml`
Toolchain: Scarb/Cairo 2.14.0, Starknet Foundry 0.55.0

## Result

No high-severity finding remains after the current manual delta review, fixes,
and regression tests. This is a project security checkpoint, not a substitute
for an independent audit. The earlier partitioned review preceded the creator
offer changes, so it is not presented as independent coverage of this release.

## Findings closed

1. **Membership state after failed token approval.** The helper now requires
   ERC-20 `approve` to return `true` before writing any membership or replay
   state. The safe-dispatcher regression test confirms a failed approval leaves
   access, offer, start, expiry, note, note-use, and allowance state empty.
2. **Subscriber-selected creator terms.** The helper now records a non-zero
   creator offer commitment with every access commitment. A publisher can reject
   altered recipient, amount, or term inputs.
3. **Client-clock expiry skew.** The ABI now accepts `duration_seconds`, and the
   helper derives `expires_at` from the same on-chain timestamp it records as
   `started_at`. This permits exact duration verification without trusting the
   browser clock.
4. **Old-note reuse.** Each note ID can be activated once globally. A second
   access commitment cannot bind itself to a note already credited to a prior
   membership.

## Verified invariants

- Only the configured STRK20 pool can activate a membership.
- Token, note ID, amount, access commitment, offer commitment, and duration must
  be non-zero.
- Duration is capped at 366 days, and expiry is derived on-chain.
- An access commitment and note ID can each be activated once.
- The helper must hold the full output amount.
- Approval is exact and must succeed before state is recorded.
- The returned open-note request preserves note ID, token, and amount exactly.
- Activation emits the access commitment, offer commitment, start, expiry,
  token, amount, and note ID.
- The unrestricted mock token is confined to the integration-test target.

External-call review found no reachable reentrancy path into state mutation: a
token callback is not the configured pool and fails `ONLY_POOL`. The sole
exception would require the trusted pool address itself to behave as the token.
The contract has no admin, upgrade, loop, signature, or unbounded-allocation
surface.

## Remaining trust and deployment gates

- The configured official pool remains the sole trusted caller and controls the
  payment path.
- Publisher access depends on correct creator-wallet note verification for the
  expected token and amount. Public helper state cannot reveal the recipient.
- A leaked creator offer link makes that offer commitment correlatable.
- No compatible Cairo static analyzer or formal verification was run.
- Recheck the exact class and pool immediately before wallet-controlled mainnet
  declaration and deployment.
